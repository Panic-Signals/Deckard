# Pad Touch Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Each sound gets a pad mode (Velocity, Poly AT, Aftertouch, CC) with Curve, Min, Max and a CC number, set on the MK3's Keyboard page through DECKARD's own built-in script mod, saved in the DECKARD block, and played by the MK3's pads.

**Architecture:** The settings live on the sound's object in the document as `deckard:` fields (so copy, move and undo carry them, as notes carry `deckard:expr`), are written to and read from a new section of the DECKARD block, and appear in the model as `Sound::pad_touch`. The script host answers new Sound parameters from them; a Lua extension written by us adds two pages to `KeyboardModePageMK3`. The MK3 thread turns pad pressure into Live events by each sound's settings.

**Tech Stack:** Rust (workspace crates model, doc, lua-host, engine; app apps/viewer), mlua, egui. Cargo always via mise.

**Spec:** docs/superpowers/specs/2026-10-24-pad-touch-design.md

## Global Constraints

- Clean room: the Lua extension is our own code; read NI's scripts only for hook names. Never copy NI code; never bundle NI scripts. Never write NI's database, libraries or favourites.
- Run cargo only as `mise exec -- cargo …`; lint/suite as `mise run lint` / `mise run test`.
- Tests never write library folders or the settings file.
- Run targeted tests while building; the full suite and lint once, before the final review.
- A project that doesn't use pad touch saves byte-identical to before (`doc-roundtrip` stays 117/117).
- Commit only when the user asks. No commit steps below.
- Settings ranges: Mode 0–3 (Velocity, Poly AT, Aftertouch, CC; default Velocity); CC 0–127 (default 1); Curve, Min, Max 0–100 % (defaults 50, 0, 100); Max ≥ Min.
- Value sent for pressure p (0..1): `min + (max − min) · shape(p, curve)`, as 0–127, where `shape` is today's `mk3_io::pad_aftertouch` with min 0, max 1.

## Review Focus

1. Keyboard mode: every pad plays the focused sound at its own pitch. Poly AT must go on each pad's pitch; in Aftertouch/CC the hardest of those pads wins, and release-to-Min fires only when the last one is let go.
2. The route or a sound's mode changes while a pad is held: the release and later pressure use the sound the pad started (`sounding`), and a pad held across a mode change never leaves a stuck value (the next pressure follows the new mode; the release still sends Min in Aftertouch/CC).
3. Sounds inserted, deleted, moved, duplicated or pasted from another project: the settings follow the sound object, and the block is written by the sounds' current indices at save.
4. Undo/redo of a knob turn on the Pad Touch page restores both the document and what the pads do next.
5. No engine running (pads queue `pending` hits): pressure is dropped, hits still play at the right velocity (Fixed in pressure modes).

Each line has its test in the owning task (Task 1: 3, 4; Task 5: 1, 2, 5).
